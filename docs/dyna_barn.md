# DynaBARN — reference notes

Reference notes compiled while planning our PufferLib `dyna_barn` env. Sources are linked
inline. All specs below are confirmed from the paper (Nair et al., SSRR 2022; PDF at
`docs/DynaBARN_Benchmarking_Metric_Ground_Navigation_in_Dynamic_Environments.pdf`)
unless explicitly marked otherwise.

---

## TL;DR

- **DynaBARN** is a **benchmark / dataset**, not a competition. No submission pipeline,
  no leaderboard, no deadline. It extends the static
  [BARN benchmark](#related-benchmarks) by adding 300 environments with dynamic
  obstacles of varying motion profiles.
- **Task**: drive a Clearpath Jackal from a fixed start (0.0, 11.0) to a fixed goal
  (0.0, −9.0) in a 20×20 m arena, without colliding with moving cylinder obstacles.
- **Robot**: Clearpath Jackal (same as static BARN) — differential drive, 500 × 430 ×
  250 mm, max speed 2 m/s, 2D LiDAR (720 beams).
- **Obstacles**: cylinders, **radius 0.5 m**, moving along **deterministic
  waypoint-based trajectories** generated by a polynomial fit. Obstacles are *not*
  reactive agents — their motion is fully predetermined and ignores the robot.
- **Dataset**:
  - 300 generated environments total (paper §I).
  - For the paper's baseline experiments: **60 sampled** — 20 easy + 20 medium + 20
    hard (paper §IV).
  - The public GitHub repo (`aninair1905/DynaBARN`) ships those 60 as
    `DynaBARN_worlds_60/` plus the generator code to make more.
- **Why we picked it over static BARN**: static BARN is reportedly saturated; DynaBARN
  is the harder dynamic variant with significant headroom (best baseline TD3 hits
  ~28% on hard).

## Task and arena

- Arena: **20 × 20 m**, walled on all four sides (back/top/bottom/front, each
  0.5 m × 20 m × 1 m walls, static — from `base_boilerplate.world`).
- Robot start: **(0.0, 11.0)** — top of the arena (paper §III-D).
- Goal: **(0.0, −9.0)** — bottom of the arena (paper §III-D).
- Robot has to traverse the full 20 m length while avoiding all moving obstacles.

## Robot

Clearpath Jackal:

| Property | Value | Source |
|---|---|---|
| Footprint (L × W × H) | 500 × 430 × 250 mm | paper Fig. 3 caption |
| Drive type | Differential (skid-steer) | Jackal spec |
| Max linear speed | 2.0 m/s | paper Fig. 3 caption |
| Linear velocity range (in baseline policies) | **v ∈ [−0.5, 2.0]** m/s (allows reverse!) | paper §IV-b |
| Angular velocity range (in baseline policies) | **w ∈ [−3.14, 3.14]** rad/s | paper §IV-b |
| Sensor | 2D LiDAR, 720-dim scan | paper §IV-b |
| Pose source | wheel odometry / `/odom` | (ROS standard) |

> **Note on reverse:** Our existing `mobile_robot/` env clamps throttle to `[0, 1]`
> (forward only). DynaBARN baselines allow reverse (`v ∈ [−0.5, 2.0]`). For the new
> env, expose `v ∈ [−v_reverse_max, v_max]` with `v_reverse_max = 0.5` so the policy
> can back out of stuck poses.

## Observation interface (paper §IV-b)

The paper's baseline policies (BC + TD3) use a **722-dimensional** observation:

| Component | Dim | Notes |
|---|---|---|
| `l` — laser scan | 720 | 2D LiDAR returns |
| `gx, gy` — local goal coordinates | 2 | x-y of the local goal from Dijkstra's global planner |

That's the **entire observation** — no robot velocity in the obs vector.
The local goal `(gx, gy)` is the next waypoint along a globally-planned Dijkstra path
through the static obstacles (the global planner ignores the dynamic obstacles).

> **For our PufferLib env**: we'll start with a slightly richer obs (add `v, w` so the
> RNN-free MLP knows current motion state) but match the 720-dim LiDAR exactly. We can
> ablate against the paper-faithful 722-dim observation later. Use a compile-time
> constant `LIDAR_BEAMS` (start at 720).

**LiDAR FOV**: **270° Hokuyo** (confirmed by the BARN Challenge 2024 lessons-learned
paper §I: "Clearpath Jackal with a 2D 270°-field-of-view Hokuyo LiDAR"). With 720
beams that is 0.375°/beam. Max range is not stated in either paper; the Hokuyo
UST-10LX is the standard fit (10 m), the UTM-30LX is also used in some Jackal
configs (30 m). Use 30 m as the upper bound in our raycast for safety.

## Action interface

Continuous 2-vector `a = (v, w)`:

- `v ∈ [−0.5, 2.0]` m/s — linear velocity (reverse allowed)
- `w ∈ [−3.14, 3.14]` rad/s — angular velocity

Published as `geometry_msgs/Twist` on `/cmd_vel` at deployment.

## Obstacle model

From paper §III-A and the GitHub generator code:

- All obstacles are **cylinders, radius 0.5 m**, base parallel to ground; orientation
  is ignored (paper §III-A).
- Each obstacle has a trajectory `⟨c_i⟩` for `i = 0..N`, where each waypoint
  `c_i = ((x_i, y_i), t_i)`.
- Trajectory generation (Algorithm 1 in paper):
  1. Sample polynomial order `n ∼ U{order_min, order_max}`.
  2. Sample `n + 1` random points in `[-10, 10] × [-10, 10]`.
  3. Fit a degree-`n` polynomial through them.
  4. Evaluate `(x_i, y_i)` at every integer x in `[-10, 10]`, drop out-of-bounds points,
     append edge-intersection points.
  5. Sort waypoints by x-coordinate (ascending or descending, each with prob. 0.5).
  6. For each segment: sample `avg_speed ∼ U{speed_min, speed_max}`,
     `avg_std ∼ U{std_min, std_max}`, then `s ∼ N(avg_speed, avg_std²)`, clipped to
     `[speed_min, speed_max]`.
  7. Segment time `Δt_i = d_i / s`, cumulative `t_i = t_{i−1} + Δt_i`.
- Movement between waypoints is **linear interpolation** (paper: "straight line to
  approximate the movement between two points", §III-A).
- In Gazebo: each obstacle is a custom C++ `ModelPlugin` scheduling
  `gazebo::common::PoseAnimation` keyframes on a 10-second loop (from
  `create_plugin_polynomial.py:make_head`).
- Obstacles are **non-reactive** — they ignore the robot entirely (paper §II-B):
  > DynaBARN does not feature multi-agent path planning where dynamic obstacles are
  > treated as agents; instead, the obstacles' motions are predetermined by waypoints
  > and it is the navigation system's responsibility to robustly avoid collisions.

## Difficulty

The paper defines difficulty along **two axes** (paper §III-C, Table I + Fig. 2):

### Axis 1 — Motion profile (per-obstacle)

| Parameter | Easy | Hard |
|---|---|---|
| `[order_min, order_max]` | `[1, 2]` | `[3, 4]` |
| `[speed_min, speed_max]` (m/s) | `[0.5, 1.0]` | `[1.0, 2.0]` |
| `[std_min, std_max]` | `[0.01, 0.1]` | `[0.1, 0.2]` |

Higher-order polynomials produce less straightforward, more erratic paths. Higher std
makes per-segment speeds less predictable.

### Axis 2 — Obstacle count (per-environment)

| Bin | Count |
|---|---|
| Low | 5 to 10 |
| High | 10 to 20 |

### Combined difficulty (Fig. 2 tree)

```
              count ∈ [5,10]                count ∈ [10,20]
              /          \                  /            \
       easy motion   hard motion     easy motion     hard motion
            |             |               |               |
          EASY         MEDIUM          MEDIUM            HARD
```

- **Easy**: low count + easy motion
- **Medium**: low count + hard motion, OR high count + easy motion
- **Hard**: high count + hard motion

For the paper's 60-world evaluation subset: **20 easy + 20 medium + 20 hard**.

## Scoring metric

The paper uses **success rate only** (paper §IV, end of "Reinforcement Learning"
paragraph):

> Since we care about the autonomous robot's capability to navigate in a completely
> collision-free manner, the success rate is the only metric we reported. Further
> metrics including traversal time and smoothness can be added for future research
> when the navigation systems are able to achieve very high success rates. The
> baselines are deployed in each environment 10 times to compute an average success
> rate.

So:

```
success_rate(method, difficulty) = mean over (env × trial) of 1[goal reached without collision]
                                 = (#successes) / (20 envs × 10 trials per env)
                                 = (#successes) / 200
```

**No traversal-time component** in the official metric. No `OT_i` (optimal traversal
time) defined for DynaBARN worlds. The "survivability metric" I had referenced earlier
is **not** from this paper.

> **For us**: report success rate as the primary metric (matches paper). We can
> additionally track success-time (AT) and a BARN-Challenge-style clipped score as
> internal-only metrics, but they don't aggregate to a number comparable with the
> paper.

## Baseline results (paper §IV, Fig. 5)

All four baselines, 10 trials × 20 environments per difficulty = 200 trials.
Numbers below are **read off the bar chart in Fig. 5** (paper does not provide a
table), so they are approximate (±0.02).

| Method | Easy | Medium | Hard |
|---|---|---|---|
| **DWA** (Dynamic Window Approach) | ~0.78 | ~0.43 | ~0.17 |
| **TEB** (Timed Elastic Band) | ~0.40 | ~0.16 | ~0.00 |
| **BC** (Behavior Cloning, 120 demos) | ~0.30 | ~0.08 | ~0.05 |
| **TD3** (Twin-Delayed DDPG, 20M steps per difficulty) | ~0.74 | ~0.60 | ~0.28 |

Notes from the paper:
- TD3 trains a **separate policy per difficulty level**, on the 20 evaluation envs of
  that level (i.e. *trained and tested on the same envs* — paper §IV "we train one
  navigation policy for 20 million time steps for each difficulty level with 20
  training environments, and test them in the same environments they are trained
  on"). This is in-distribution evaluation, not generalisation.
- DWA + TEB hyperparameters tuned for hard envs, then fixed across all eval (paper
  §IV-a).
- BC uses 60 demos from DynaBARN + 60 demos from static BARN = 120 total (paper
  §IV-b).
- The 720-dim laser + 2-dim goal `(gx, gy)` is the obs for both BC and TD3 (paper
  §IV-b).
- Network architecture (paper Fig. 4):
  - Actor: `722 → 512 → 256 → 128 → 64 → 32 → 2` (tanh activations).
  - Critic: same except final layer outputs 1 (value).

### Implications

- **Hard envs are unsolved.** TD3 at 28% leaves 72% of room. This is where
  improvements show.
- TD3's training protocol is **train-on-test** — a real generalisation benchmark
  would train on a held-out set and evaluate on these 60. We should do the latter.
- DWA being surprisingly competitive (78%/43%/17%) is a hint that a model-based
  fallback layer (DWA-style velocity-window check on top of an RL policy) might be
  worth trying.

## Current SOTA (follow-up papers)

DynaBARN itself has no maintained leaderboard. The two main published follow-ups that
explicitly evaluate on the public 60-world subset are **Dyna-LfLH** (2024) and
**LfH-CP** (2025). Their reported numbers are summarised below.

### Dyna-LfLH (Ghani et al., 2024) — [arXiv 2403.17231](https://arxiv.org/abs/2403.17231)

- **Idea**: extends Learning-from-Hallucination to dynamic envs. Trains by collecting
  10 minutes of self-supervised exploration in an *open* space, then hallucinating
  dynamic obstacle trajectories around the recorded ego-trajectory to fabricate
  imitation-learning data.
- **Architecture**: MLP with a stack of `L` past LiDAR scans as input (`L ∈ {1, 3,
  5, 10}` tried).
- **Eval protocol**: 60 envs × 3 trials = **180 trials**. A single gentle collision =
  failure. Recovery behaviors disabled (focuses pure-planner performance).
- **Reported headline**: "Dyna-LfLH with 5 history scans outperforms BC and achieves
  the best performance across the board" (paper §IV-B). Specific bar-chart values are
  in their Fig. 4 but not transcribed in a table.
- **Reference number** (from the LfH-CP paper's re-implementation): **22.5% overall
  success rate** across all 60 envs. The LfH-CP paper attributes the low number to
  mode collapse in the hallucination process.

### LfH-CP (Hallucinating Critical Points, 2025) — [arXiv 2509.26513](https://arxiv.org/abs/2509.26513)

- **Idea**: factorises hallucination into (a) finding "critical points" — where/when
  obstacles must appear to make an existing motion plan optimal — and (b)
  procedurally generating diverse trajectories through those points. Avoids the mode
  collapse that hurts Dyna-LfLH.
- **Architecture**: causal Transformer (2 encoder layers, 2 heads, 256-d FF) over
  five past LiDAR scans + five past actions; predicts five future actions. LiDAR
  encoded by a 2-layer 1D CNN (kernel 5) to a 256-d embedding.
- **Eval protocol**: 60 envs × 2 trials = **120 trials**.
- **Reported number**: **30.83% overall success rate** vs. Dyna-LfLH's 22.5%.
  Verbatim from paper §IV-D:
  > "LfH-CP achieves a higher success rate at 30.83% [over 60 envs × 2 trials =
  > 120 trials], showing that hallucinated critical points provide strong
  > navigation performance. In contrast, Dyna-LfLH underperforms with success
  > rates of 22.5%"
- **Verified 2026-05-14**: both numbers are **overall averages across all 60
  worlds (easy + medium + hard combined)**, not hard-bin-only. Paper does not
  publish a per-difficulty breakdown.
- **Caveat**: direct comparison to the DynaBARN-paper TD3 number (which is
  *per-difficulty*, *in-distribution*) is not apples-to-apples.

### Comparison table (best public DynaBARN-60 numbers)

Overall success rate across the 60-world subset, averaged across difficulties.

| Method | Overall success | Eval protocol | Source |
|---|---|---|---|
| TEB | not reported overall (≈ 19% if avg over difficulties) | 200 trials per difficulty | DynaBARN paper Fig. 5 (read from chart) |
| BC | not reported overall (≈ 14%) | 200 trials per difficulty | DynaBARN paper Fig. 5 |
| DWA | not reported overall (≈ 46%) | 200 trials per difficulty | DynaBARN paper Fig. 5 |
| TD3 (per-difficulty, **train=test**) | not reported overall (≈ 54%) | 200 trials per difficulty, **in-distribution** | DynaBARN paper Fig. 5 |
| **Dyna-LfLH** | **22.5%** | 180 trials | LfH-CP paper Fig. 7 |
| **LfH-CP** | **30.83%** | 120 trials | LfH-CP paper Fig. 7 |

> **Caveat**: TD3's higher per-difficulty numbers are *train-on-test*. The 60-trial
> protocols (Dyna-LfLH, LfH-CP) are true generalisation — train on hallucinated /
> self-supervised data, evaluate on the public 60 worlds. Generalisation numbers in
> the 20–30% range are the honest baseline to beat.

### LiCS (Damanik et al., 2024) — adjacent, BARN-only

- Won the 3rd BARN Challenge (ICRA 2024) **simulation qualifier (0.4762 score) and
  physical finals (6/9 trials)** with a Transformer + BC + safety check.
- **Trained on static BARN only**, not DynaBARN. Listed here because it's the
  strongest LiDAR→action policy on the BARN family of benchmarks.
- Paper: [J. J. Damanik et al., "LiCS: Navigation using learned-imitation on
  cluttered space," 2024](https://arxiv.org/abs/2403.18016).
- Method: ViT-style encoder + Transformer decoder, BC from a classical expert
  (KUL+FM, 2nd BARN Challenge winner) with Gaussian noise injection (σ=0.25), plus a
  geometric safety-check layer that triggers reversing/in-place rotation.

### 4th BARN Challenge (ICRA 2025, Atlanta) — first competition to include DynaBARN

Sources: GMU 2025 challenge page summary; [MTU news release (Jul 2025)](https://www.mtu.edu/news/2025/07/mtu-robotics-lab-wins-international-autonomous-navigation-competition.html);
3rd-challenge paper §VI ("Future Plans"). No formal lessons-learned paper has been
posted as of 2026-05-14.

- **Dynamic-obstacle rules**: collisions with *static* obstacles still = total
  failure; collisions with *dynamic* obstacles → penalty only, not termination
  (3rd-challenge paper §VI). The exact bonus formula is not in any public source
  I could find — wait for the 2025 lessons-learned paper.
- **Format**: 9 simulation teams, 8 invited to physical, 4 attended (Atlanta).
- **Physical obstacle**: iRobot Create robots used as the dynamic obstacles in the
  physical course (GMU 26 page mention).
- **Results**:
  - 🥇 **RRSL** (Michigan Tech, Mazen + Yazdipaz + Mateyaunga). Approach: *rule-based,
    no learning* — pure conditional logic ("if you see this, do that"). Entered the
    physical stage in 7th place from sim, won by margin. Round 1: 5/5 perfect, no
    collisions (only team to do so). Round 2: 4/6. Round 3: 1.
  - 🥈 **RobotiXX** (George Mason University)
  - 🥉 **UVA AMR** (University of Virginia)
- **What it tells us**:
  - A well-tuned rule-based system beat all learning approaches when dynamic
    obstacles were introduced. Generalisation under distribution shift is still hard
    for learned policies.
  - Per the 3rd-challenge paper's discussion of LiCS: even *winning* learning
    policies need a separate safety-check layer at deploy time. RRSL skipped the
    learning entirely.
- **Open**: which teams' DynaBARN sim scores were what — needs the 2025
  lessons-learned paper.

## Related benchmarks

- **BARN** (static): 300 worlds, same Jackal robot, no dynamic obstacles. Saturated.
  arXiv 2008.13315.
- **BARN Challenge 2026**: annual physical + sim competition built on static BARN.
  Hard deadline 2026-05-08 (passed). Score = `s_i = 1[success] · OT_i / clip(AT_i,
  2·OT_i, 8·OT_i)`. **Note**: this clipped-time metric is the *BARN Challenge*'s
  metric, not the paper's. DynaBARN paper uses success rate only.
- **Pedsim / SEAN 2.0 / Arena-Bench / SocNavBench**: pedestrian-focused testbeds.
  All use a single motion model (social-force or ORCA) so obstacles within one
  testbed share a motion profile. DynaBARN's contribution is varying the motion
  profile per obstacle (paper §II-B).
- **Hallucinating-style methods** (LfH → LfLH → Dyna-LfLH → HCP): all use
  BARN/DynaBARN as their evaluation testbed.

## Implications for our PufferLib `dyna_barn` env

(See `logger.md` for the up-to-date implementation plan.)

1. **Arena**: 20 × 20 m walled. Fixed start (0, 11), fixed goal (0, −9).
2. **Robot**: differential drive, `v ∈ [−0.5, 2.0]`, `w ∈ [−3.14, 3.14]`. Need to
   extend our existing `mobile_robot/` action space to allow reverse.
3. **Observation**: `(720-dim LiDAR, goal_dx, goal_dy)` minimum to match paper.
   Consider also exposing `(v, w)` (deviates from paper baseline but is cheap info).
   `LIDAR_BEAMS = 720` as a compile-time constant.
4. **Obstacles**: cylinders (r=0.5 m), waypoint trajectories with per-segment linear
   interpolation. C-side state per obstacle: `{radius=0.5, [(t_i, x_i, y_i)]_i, idx}`
   where `idx` is the active segment. Time-advance and lerp on each step.
5. **Worlds**: 60 baked from `aninair1905/DynaBARN`. One-off Python preprocessor
   (`bake_worlds.py`) parses the SDF + plugin `.cc` sources into a flat binary; C reads
   at reset.
6. **Difficulty bins**: replicate the easy / medium / hard split. Each training run
   targets one difficulty, matching the paper's protocol *or* train on a mixed
   curriculum (our call — paper does the former).
7. **Training/eval split**: unlike the paper, **train on a separate set of generated
   worlds** and evaluate on the public 60. This is the standard generalisation
   protocol and gives us numbers comparable to the paper as a lower bound (since
   train-on-test always wins).
8. **Reward (training-time)**: Δ-distance shaping + Gaussian obstacle repulsion
   (using closest LiDAR return as the distance term) + success bonus + collision
   termination with penalty. Keep our existing reward design as a starting point.
9. **Eval metric**: success rate as primary (paper-faithful). Internal: success rate
   per difficulty bin, mean traversal time, collision count.
10. **Target**: beat TD3's ~74/60/28%. Plausible reach: 85/70/40% with a properly
    generalising policy.
